# Take Time 单房间双人 Web 原型设计方案

## 项目目标

基于 Libellud 合作桌游《Take Time》的核心体验，开发一个私用的在线 Web 原型。初版只支持两名玩家同时游玩：用户 A 登录后进入唯一房间，用户 B 登录后加入同一个房间，两人准备就绪后由房主选关开始游戏。

项目重点是验证核心机制是否适合在线化：先共同观察时钟并讨论策略，再进入有限沟通阶段，玩家轮流暗置手牌，仅靠有限的“提示标记”传递信息，最后揭示并检查区段条件。已通关的关卡会被记住，方便队伍按顺序推进。

## 游戏范围

初版只做一个全局房间，不做多房间系统，也不考虑高并发。

- 最多 2 名玩家。
- 使用昵称登录，不做邮箱、密码或第三方账号。
- 第一名进入的用户占据玩家 A 座位，第二名进入的用户占据玩家 B 座位。
- 第三名用户进入时直接提示房间已满。
- 登录成功后进入房间，每名玩家有“准备”按钮。
- **第一个准备的玩家成为房主**；两人都准备后，房主端弹出“是否开始游戏”确认。
- **房主负责设置参数、选择关卡、开始游戏**；非房主只能准备/取消准备。
- 玩家开始前可以设置讨论时间、每回合思考时间和提示标记数量（房主设置）。
  - 讨论时间默认 5 分钟，可选 5、10、15、20 分钟。
  - 每回合思考时间默认 5 秒，可选 5、6、7、8、9、10 秒。
  - 提示标记默认 3 个，可选 2、3、4 个（**全队共用**）。
- 关卡共 N 关（如 40 关，具体数量随关卡内容确定）；房主在选关界面选择任意一关进入，**已通关的关卡会标记显示**。
- 通过当前关后**按顺序直接进入下一关**（如从第 28 关开始，通关后进入第 29 关）。
- **已通关进度需要持久化**：服务重启或玩家重新登录后仍然保留。

初版不使用官方美术、官方完整规则文本或官方 40 个关卡内容。可以保留“受 Take Time 启发的合作时钟谜题”这一产品定位，但公开部署时应避免使用未经授权的官方素材和完整复刻内容。

## 技术栈

建议使用一个 Node 服务同时承载前端静态资源和实时通信。

- 前端：Vite + React + TypeScript
- 后端：Express + Socket.IO
- 运行时状态：服务端单进程内存对象（房间、当前对局）
- 进度持久化：Railway Volume 上的一个 JSON 文件（或轻量 DB），仅存“已通关进度 + 设置”这类需要跨重启保留的数据
- 部署：Railway 单服务部署

Railway 上只需要一个 Web 服务。构建时生成前端静态文件，运行时由 Express 提供页面，并通过 Socket.IO 处理两名玩家之间的实时同步。进行中的对局放内存，已通关进度落盘到 Volume。

## 单房间双人逻辑

服务端维护一个全局 `gameRoom` 对象，不创建房间列表。

`gameRoom` 建议包含：

```
gameRoom {
  players: { A?: Player, B?: Player }                 // 两个固定座位
  ready: { A: boolean, B: boolean }                   // 各自准备状态
  host: null | 'A' | 'B'                              // 第一个准备的玩家成为房主
  phase: 'waiting' | 'levelSelect' | 'discussion' | 'placing' | 'reveal' | 'result'
  settings: { discussionMinutes, thinkSeconds, hintMarkerCount }   // 房主设置
  progress: { clearedLevels: number[], totalLevels }  // 已通关关卡集合（持久化）
  currentLevelIndex                                   // 当前所在关卡
  currentChallenge: Challenge                         // 当前挑战（见“关卡与挑战模型”）
  hands: { A: HandCard[6], B: HandCard[6] }           // 两名玩家各自的私有手牌
  playedCount: { A: number, B: number }               // 各玩家已打出的牌数
  placements: PlacedCard[][6]                         // 6 个固定区段上的暗置卡牌
  hintMarkers: { total, used }                        // 全队共用的提示标记
  turn: null | 'race' | 'A' | 'B'                     // 当前出牌权
  pendingHint: null | { player, cardRef, deadline }   // 出牌后的提示决策窗口
  chat: Message[]                                     // 讨论阶段的聊天记录
  timers: { phaseDeadline, turnDeadline, hintDeadline }
  revealResult: null | { segmentSums: number[6], conditions: [{ desc, pass }] }
  failureReason: null | 'rule-unmet' | 'timeout'
}

HandCard  { value, visibleToOwner }       // value 服务端始终知道；visibleToOwner 决定是否发给本人
PlacedCard{ owner, value, revealed }      // revealed=true 表示用了提示标记，永久正面朝上
```

`progress` 来自持久化文件，服务启动时加载；每次通关后更新并落盘。

登录规则：

- 用户输入昵称后连接 Socket.IO。
- 如果玩家 A 为空，分配到 A。
- 否则如果玩家 B 为空，分配到 B。
- 否则拒绝加入并提示房间已满。
- 如果连接断开，座位可以短时间保留；同昵称重连时优先恢复原座位。

## 房主与准备逻辑

- 两名玩家就座后，各自可切换“准备”状态（`player:ready`）。
- **第一个进入准备状态的玩家成为房主**（`host`）。房主身份在本局房间内保持。
- 当 A、B **都准备就绪**时，房主端出现“开始游戏”确认（前端依据 `ready` 与 `host` 渲染，无需额外事件）。
- 房主点击开始（`game:start`）→ 进入 `levelSelect`。
- 设置参数（`settings:update`）、选关（`host:selectLevel`）、开始/进入下一关/返回选关都**仅房主可操作**；服务端校验身份。

## 关卡与挑战模型

时钟**固定 6 个区段**，每一关区段数都是 6，但条件要求各关不同（具体关卡设计由用户后续提供）。

```
Challenge {
  id, name, levelIndex,
  segmentCount: 6,
  centerCap: number | null,  // 时钟中心值：null = ∞（每区段无上限）；数字 = 每段总和 ≤ 该值
  deck: number[12],          // 该关使用的 12 张牌（数值待定）
  conditions: Condition[]    // 本关需同时满足的条件（组合 = AND）
}
```

> `centerCap` 是**时钟（关卡）级**属性，对全部 6 个区段统一生效；加载关卡时按「每段总和 ≤ centerCap」并入条件校验（等价于一条 `max-sum-each` 条件），`null` 时不施加上限。前端把它显示在钟面中心（数字或 ∞）。详见 [rules.md · 时钟中心值](../rules.md) 与 [关卡词汇表](../levels/README.md)。

条件类型（覆盖原创挑战，避免复刻官方关卡）：

- 单区段：总和等于目标、总和落在范围内、必须为奇/偶、至少 1 张牌（空间目标）。
- 跨区段：若干区段总和递增、递减、相邻区段总和差值满足限制。
- 组合：以上多个条件同时满足。

**校验引擎**：输入 6 个区段的牌值总和，输出 `{ pass: boolean, failedConditions: [...] }`。失败项用于揭示与复盘提示。所有判定由服务端在揭示阶段执行。

## 手牌与可见性

- 发牌每人 6 张。玩家**只能看到中间 4 张**，**两端 2 张对自己也是暗的**（盲牌）。
- 暗牌**也可以打出（盲打）**；打出后在桌上同样不显示。
- 当某玩家**自己累计打出 2 张牌后**，其手里剩余的暗牌**对其本人翻开**（仅对本人，不对队友）。
- 服务端始终知道每张手牌的真实值；`player:hand` 私有事件对“对己暗牌”遮蔽牌值，直到上述翻开条件满足。

## 桌面可见性与提示标记

- 桌上**所有打出的牌，对双方都是暗的**——owner 自己也看不到已打出的牌值。
- **唯一例外**：打牌时使用了**提示标记**的那张牌，**永久正面朝上**摆在桌上，**双方都能看到**。这是无沟通阶段唯一的信息传递手段。
- 提示标记**全队共用**，开局可设 2、3、4 个（默认 3），先用先得。
- **每打出一张牌后**，给该玩家弹出一个 **5 秒 yes/no 弹框**决定这张要不要翻开示意队友：
  - 选 yes 且全队还有剩余标记 → 消耗 1 个标记，该牌永久翻开。
  - 选 no / 5 秒超时 / 标记已用完 → 不翻开，**不判负**，正常继续。
- **时序**：提示窗口期间游戏暂停，玩家选完（或超时）后才把回合交给对方。
- 最终揭示阶段会把所有暗牌翻开，提示标记翻开的牌保持正面。

## 游戏阶段

初版游戏流程使用固定状态机：`waiting → levelSelect → discussion → placing → reveal → result`。

1. `waiting`
   - 等待两名玩家加入；各自可切换准备状态。
   - 第一个准备的玩家成为房主；两人都准备后房主端出现“开始游戏”确认。
   - 房主可在此调整 `settings`。
   - 房主确认开始（`game:start`）→ 进入 `levelSelect`。

2. `levelSelect`
   - 展示全部关卡（1…N），**已通关的关卡标记显示**（来自 `progress.clearedLevels`）。
   - **房主选择任意一关**（`host:selectLevel`）→ 加载该关并进入 `discussion`。

3. `discussion`
   - 展示当前时钟挑战、6 个区段信息和本关目标。
   - 玩家可以聊天讨论策略；此时**不能查看自己的手牌**。
   - 显示讨论倒计时，默认 5 分钟；房主可点击“开始游戏”（`game:beginPlacement`）提前结束讨论。
   - 如果没有提前开始，讨论时间结束后自动进入 `placing`。

4. `placing`
   - 进入瞬间：发牌（每人 6 张，中间 4 张可见、两端 2 张对己暗），**禁用聊天**，立即开始第一手的思考时间倒计时。
   - **第一手 = 抢出牌**：无预设先手，A/B 都可在思考时间内出牌；**第一个有效 `card:place` 生效**，占据第一手，另一方该手被锁。
   - 之后**严格交替**（先手方 → 另一方 → 交替，直到 12 张放完，自然每人 6 张）。
   - 每次出牌：选 1 张手牌（含盲牌）面朝下放到任意区段（区段 0–5，可放多张）；不能移动或查看已暗置的牌。
   - **出牌后进入提示决策子步骤**（`pendingHint`）：游戏暂停，5 秒 yes/no，决议后才换手。
   - 当某玩家自己打满 2 张后，翻开其剩余暗牌（仅对本人）。
   - 界面显示当前出牌倒计时与提示决策倒计时。
   - **超时判负**：抢出牌期双方都没出 → 判负；交替期当前玩家超时未出 → 判负。（提示窗口超时不判负。）
   - 12 张全部放完后**自动**进入 `reveal`。

5. `reveal`
   - 翻开所有暗置卡牌（提示标记的牌已正面）。
   - 按 6 个区段统计数值总和。
   - 运行关卡条件引擎：检查每个区段至少有 1 张牌（如该关要求）、**若 `centerCap` 非 null 检查每个区段总和 ≤ centerCap**，并检查当前挑战的全部条件。

6. `result`
   - **成功**：把 `currentLevelIndex` 记入 `progress.clearedLevels` 并**落盘持久化**；房主可进入下一关（`game:next`，顺序 `currentLevelIndex + 1`，直接到下一关 `discussion`）。若已是最后一关，提示全部通关。
   - **失败**：房主可重试当前关（`game:retry`）。
   - 房主也可返回选关界面（`host:backToLevelSelect`）。
   - 展示 `revealResult`（各区段总和、各条件通过/失败）与 `failureReason`，方便复盘。

## Socket 事件

客户端到服务端：

- `player:join`：提交昵称并加入唯一房间。
- `player:leave`：主动离开或释放座位。
- `player:ready`：切换准备状态（第一个准备者成为房主）。
- `settings:update`：**房主**更新讨论时间、思考时间、提示标记数量。
- `game:start`：**房主**确认开始 → 进入选关界面。
- `host:selectLevel { levelIndex }`：**房主**选择关卡 → 进入该关讨论。
- `game:beginPlacement`：**房主**提前结束讨论，直接进入 `placing` 并发牌。
- `chat:send`：讨论阶段发送聊天消息。
- `card:place`：当前玩家（或抢先手期任一玩家）选择手牌和目标区段。
- `hint:decide { decision: 'yes' | 'no' }`：出牌后在提示窗口内决定是否翻开该牌。
- `game:retry`：**房主**失败或复盘后重试当前挑战。
- `game:next`：**房主**成功后进入下一挑战（顺序）。
- `host:backToLevelSelect`：**房主**返回选关界面。
- `room:reset`：开发或异常情况下重置唯一房间（不清除已通关进度）。

服务端到客户端：

- `room:state`：广播完整公共房间状态（含 `ready`、`host`、`progress.clearedLevels`、`currentLevelIndex`、`turn`、剩余提示标记、`pendingHint`，并对 `revealed=false` 的桌面牌遮蔽牌值）。
- `player:hand`：只发给对应玩家的私有手牌（对己暗牌遮蔽牌值）。
- `room:error`：加入失败、越权操作、阶段错误等提示。
- `timer:sync`：同步讨论倒计时、当前出牌倒计时或提示决策倒计时。
- `game:result`：揭示后的成功或失败结果。

所有关键操作都应由服务端校验，前端只负责展示和发送意图。计时判定以服务端时间为准。

## 服务端校验

服务端作为权威状态来源，负责校验：

- 当前是否已经有两名玩家、是否处于允许操作的阶段。
- **准备/房主**：`player:ready` 仅就座玩家在 `waiting` 可用；第一个准备者被记为 `host`。
- **房主专属操作**：`settings:update`、`game:start`、`host:selectLevel`、`game:beginPlacement`、`game:next`、`game:retry`、`host:backToLevelSelect` 仅 `host` 可执行。
- `game:start` 仅在两人都准备且处于 `waiting` 时有效；`host:selectLevel` 仅在 `levelSelect`，且 `levelIndex` 合法。
- 目标区段索引在 **0–5** 范围内。
- **抢先手并发仲裁**：抢出牌期首个有效 `card:place` 生效，其余拒绝（`turn` 已推进）。
- 交替期是否轮到该玩家出牌；玩家是否拥有要出的那张牌；**盲牌允许打出**（不得因 `visibleToOwner=false` 拒绝）。
- 当前玩家是否在思考倒计时内完成出牌（超时判负）。
- `hint:decide` 仅在 `pendingHint` 期、由该出牌玩家、在 deadline 前有效；标记不得超额。
- 玩家自己打满 2 张后翻开其剩余暗牌。
- 是否已经放满 12 张牌；揭示时是否满足当前关卡条件。
- 通关后写入 `progress.clearedLevels` 并落盘持久化。

前端不能自行决定胜负。手牌可见性、桌面暗牌牌值都由服务端按规则遮蔽后再下发。

## Railway 部署假设

初版可以直接部署在 Railway 的单实例 Node 环境中。

- 使用 `npm run build` 构建前端。
- 使用 `npm start` 启动 Express + Socket.IO 服务。
- 服务监听 `process.env.PORT`。
- **挂载一个 Railway Volume**，把“已通关进度 + 设置”存成 JSON 文件，做到跨重启/重新登录保留。
- 进行中的对局（手牌、暗置牌、倒计时等）仍只放内存，服务重启时丢失当前对局是可接受的——但**已通关进度不丢**。
- 不支持多实例横向扩容，因为房间状态存在单进程内存中。

这个限制符合当前需求：只有一个房间、两名玩家、不考虑高并发。

## 测试计划

本地测试：

- 打开两个浏览器窗口，分别用两个昵称登录；验证第一个用户成为 A、第二个成为 B、第三个被提示房间已满。
- 验证两人都需点击准备；**第一个准备者成为房主**；两人都准备后**房主端出现“开始游戏”确认**，非房主没有该按钮。
- 验证设置、选关、开始、进入下一关、重试、返回选关**仅房主可操作**。
- 验证选关界面展示全部关卡，**已通关的被标记**；房主选一关后进入该关讨论。
- 验证通关后**按顺序进入下一关**（如 28 → 29）；失败可重试当前关。
- 验证讨论时间可选 5、10、15、20 分钟（默认 5）、思考时间可选 5–10 秒（默认 5）、提示标记可选 2–4 个（默认 3）。
- 验证讨论阶段可以聊天、显示倒计时、可提前开始、超时自动进入出牌；发牌后聊天被禁用。
- 验证每人 6 张，**自己只见中间 4 张、两端 2 张暗**；第一手倒计时立即开始。
- 验证**抢先手**：A/B 任一可出第一手，先出者占手、另一方被锁；之后严格交替，最终每人出 6 张。
- 验证**盲打**：暗牌可被选中打出；打出后桌上不显示牌值。
- 验证**打满 2 张**：该玩家剩余暗牌对其本人翻开，队友仍看不到。
- 验证**提示标记**：出牌后弹 5 秒 yes/no；yes 且有余额 → 该牌永久正面朝上（双方可见）、计数 -1；no/超时/无余额 → 不翻、不判负；窗口期间暂停、决议后才换手；全队共用额度先用先得。
- 验证**超时判负**：抢先手双方都没出 → 判负；交替期当前玩家超时 → 判负。
- 验证 12 张全部放完前不能揭示；放满后**自动**揭示。
- 验证揭示后正确统计 6 个区段总和；空区段按条件判失败；关卡条件（总和/范围/奇偶/递增/递减/差值/组合）校验正确，失败时展示失败项。
- 验证刷新页面或短暂断线后，同昵称可以回到原座位。
- 验证**进度持久化**：通关若干关后重启服务/重新登录，已通关标记仍在。

Railway 测试：

- 部署后用两台设备或两个浏览器访问同一个 Railway URL。
- 验证 Socket.IO 连接正常、两名玩家可以实时看到对方动作。
- 验证服务重启后进行中的对局清空可接受，但**已通关进度（Volume 中的 JSON）仍然保留**。

- 关卡内容：**总关卡数 N（如 40）**与 **6 个区段各关的具体条件设计**。
- 进度持久化文件的具体格式（建议：`{ clearedLevels: number[], settings }` 的单个 JSON）。

## 版权与素材边界

本项目初版定位为私用原型，应避免直接复制官方内容。

- 不复制官方完整规则书文本。
- 不使用官方美术、图标、卡牌图或时钟插画。
- 不逐字复刻官方 40 个挑战。
- 可以用中文总结核心机制，作为开发参考。
- 可以设计原创示例关卡，用于验证在线玩法。

如果未来计划公开发布，需要进一步处理命名、视觉、关卡设计和授权问题。更稳妥的公开方向是改成原创标题、原创美术、原创关卡，只保留“有限沟通合作时钟谜题”的抽象玩法灵感。
