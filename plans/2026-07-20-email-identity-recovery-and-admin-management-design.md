# 第一阶段邮箱登录、账号维护与后续验证设计

> 状态：现行执行方案；后端 Phase 1–3 与生产登录/注册已完成，账号资料和管理员账号页待生产对接（2026-07-21）  
> 决策记录：[ADR-0007](../docs/adr/0007-account-password-lifecycle-and-admin-management.md)  
> 前端总入口：[frontend-ui-plan.md](../docs/frontend-ui-plan.md)  
> 第一阶段 Prototype：`/prototype/account/login` · `/prototype/account/register` · `/prototype/account/security` · `/prototype/admin`

## 1. 本期结论

第一阶段使用“邮箱 + 个人密码”登录，但**不验证邮箱、不发送邮件、不提供密码找回**。

| 数据或凭证 | 第一阶段职责 |
| --- | --- |
| `playerId` | 服务端生成的稳定内部主键；进度、会话和审计只关联它 |
| 邮箱 | 唯一登录标识；只校验格式与是否已被占用，不证明邮箱属于注册者 |
| 个人密码 | 玩家身份验证凭证；只保存安全哈希，任何人都不能查看原文 |
| 昵称 | 游戏内展示资料；注册时设置，登录后可修改，不参与登录 |
| 头像 | 游戏内展示资料；未上传时由 `playerId` 派生选取 2 张默认图之一，允许重复 |
| 房间密码 | 单房间准入口令；登录或注册后用于进入房间，不证明个人身份 |

本期明确不做：

- 邮箱验证码、验证状态、验证邮件和安全通知；
- `/account/recover`、登录页“忘记密码”入口和邮件重置链接；
- 恢复密钥、管理员签发重置凭证或管理员代设玩家密码；
- Resend、SMTP、邮件 Provider、发信域名和相关环境变量；
- 旧昵称账号升级入口。

原因是 Resend 等事务邮件服务仍需要可验证的自有发信域名。域名尚未准备好时，展示邮箱验证或找回功能只会制造无法兑现的承诺。

## 2. 安全边界与产品提示

未验证邮箱在第一阶段本质上是“长得像邮箱的用户名”，不是账号所有权证明。因此必须接受并明确展示以下限制：

- 用户可能误填邮箱，也可能填写并不属于自己的邮箱；系统无法判断。
- 忘记个人密码后，现阶段无法恢复原账号。
- 管理员无法确认申请者是否为本人，因此不能重置、查看或替换玩家密码。
- 管理员也不能替玩家修改登录邮箱；玩家只能在已登录且能提供当前密码时自行修改。
- 未来开启邮箱验证前，开发期账号库应备份后重建或执行专门的邮箱认领迁移，不能把未验证邮箱直接标成“已验证”。

登录页和注册页各展示一句等价的短提示，必须同时点明「不验证邮箱」与「无法找回密码」两件事。当前实现用词：

> 登录页：当前不验证邮箱，也不支持找回密码，请妥善保管个人密码。
> 注册页：当前不验证邮箱且无法找回密码。请确认填写正确。

不使用“已绑定”“已验证”“可找回”等容易产生错误安全预期的措辞。

## 3. 玩家流程

### 3.1 首页登录

无玩家会话时，`/` 默认显示简洁认证卡片，并激活“登录”Tab。只保留两个 Tab：

- 登录：`/`
- 注册：`/account/register`

登录字段：

1. 邮箱；
2. 个人密码；
3. 房间密码。

服务端**先验证房间密码，通过后才查询账号并做密码校验**。顺序不能反：scrypt 是刻意设计的昂贵运算，若先做密码校验，任何不知道房间密码的人都能用任意邮箱触发一次完整 scrypt，形成放大攻击。房间密码在此充当廉价前置闸门，房间密码错误时不触达账号仓库。

错误文案分两类：

- **房间密码错误**使用独立文案（“房间密码错误”）。它是共享准入口令，不是个人秘密，也不参与账号身份；与账号错误合并只会让用户分不清是房间密码打错了还是账号有问题。
- **账号相关失败**统一为“邮箱或密码不正确”，不区分“邮箱不存在”“密码错误”“账号已停用”，避免账号枚举。

### 3.2 注册

注册字段：

1. 邮箱；
2. 个人密码；
3. 确认密码；
4. 游戏昵称；
5. 房间密码。

提交后服务端依次完成：

1. 规范化邮箱并校验基础格式；
2. 检查邮箱唯一性、昵称规则、密码规则和房间密码；
3. 生成 `playerId`，写入账号并创建会话；
4. 直接进入大厅。

没有“发送验证码”和“输入验证码”的中间步骤。邮箱被占用时可明确提示“该邮箱已注册”；这是注册表单的正常冲突反馈。

### 3.3 昵称修改

入口：`/account/security`。

- 昵称可由玩家随时修改；
- 修改昵称不改变 `playerId`、登录邮箱、通关进度、当前座位或 Agent 记忆；
- **昵称必须账号级唯一，不允许重复**。唯一性基于 `nicknameNormalized`（trim + 大小写与全角/半角规范化）判定，注册与改名都要校验；冲突时只提示“该昵称不可用”，不透露占用者是谁。
- 唯一性的目的是避免唯一全局房间中出现同名玩家造成误判，**不承担身份验证职责**：昵称不能作为登录键，也不能作为任何恢复流程的查询键。
- 改名成功后按 `playerId` 原子更新当前座位与公共状态投影，并记录 `nicknameChangedAt`。

### 3.4 修改个人密码

有效会话 + 当前密码 + 新密码 + 确认新密码：

- 成功后递增 `credentialVersion`，其他会话据此自动失效（语义见 §5）；
- 当前设备立即换发携带新版本的会话，不中断正在进行的对局；
- 管理员只能看到“最近修改时间”，不能看到密码、哈希或新密码。

忘记当前密码时不提供重置路径。界面只展示本期限制，不展示灰掉的找回按钮。

### 3.5 修改登录邮箱

有效会话 + 当前密码 + 新邮箱：

- 新邮箱只做规范化、格式与唯一性校验；
- 校验通过后立即替换登录标识并递增 `credentialVersion`，其他会话据此自动失效（语义见 §5）；
- 当前设备立即换发携带新版本的会话；
- 明示“新邮箱不会被验证，修改后请使用它登录”。

该能力没有验证码、旧邮箱通知或等待确认状态。未来启用验证后必须重新设计为“双邮箱通知 + 新邮箱验证”的完整流程。

## 4. 管理员账号维护

统一入口：`/admin`，登录后进入：

- `/admin/accounts`：注册账号维护；
- `/admin/room`：当前房间与座位维护。

### 4.1 账号列表可展示

- `playerId`；
- 当前昵称与头像；
- 脱敏邮箱，并标注“未验证登录标识”；
- 账号状态：正常 / 停用 / 已删除；
- 在线或在座状态；
- 注册时间、最近改密时间。

管理员默认不需要看到完整邮箱。完整邮箱应加密保存，只在服务端登录查找与玩家本人修改时使用。

### 4.2 管理员可以执行

- 搜索与筛选账号；
- 强制登出全部玩家会话；
- 停用 / 恢复账号（停用保留邮箱与昵称占用，见 §5）；
- 软删除账号（需二次确认，并保留必要审计记录；释放邮箱与昵称占用，见 §5）；
- 在房间页把玩家请出当前座位；
- 按既有规则显式接管房间。

### 4.3 管理员不能执行

- 查看个人密码或密码哈希；
- 代设、重置或生成玩家密码；
- 发送找回邮件或验证邮件；
- 将邮箱标记为已验证；
- 代玩家更换登录邮箱；
- 把“请出房间”等同于停用或删除账号。

`/admin/accounts` 与 `/admin/room` 可以在同一管理员壳层中切换，但房间动作和账号动作保持明确分区。

## 5. 数据模型

建议账号记录如下。`schemaVersion` 保持在**文件级**（沿用现有 `AccountsFile` 结构），不写进每条记录：

```ts
interface AccountsFileV2 {
  schemaVersion: 2;
  accounts: PlayerAccountV2[];
}

interface PlayerAccountV2 {
  playerId: string;
  nickname: string;
  nicknameNormalized: string;
  avatar: string | null;

  emailLookupHash: string;
  emailCiphertext: string;
  emailIv: string;
  emailAuthTag: string;
  emailKeyVersion: number;

  passwordSalt: string;
  passwordHash: string;
  kdf: AccountKdfParams;

  credentialVersion: number;
  status: "active" | "disabled" | "deleted";
  createdAt: number;
  updatedAt: number;
  nicknameChangedAt: number | null;
  passwordChangedAt: number;
  deletedAt: number | null;
}
```

第一阶段不需要 `emailVerifiedAt`、verification token、reset token 或 recovery key 字段。未来正式启用邮箱验证时再通过 schema migration 增加，不提前写入虚假的验证状态。

### `credentialVersion` 的作用

`credentialVersion` 是账号当前凭证的单调计数器，**它是“撤销其他会话”的实现依据**：

- 签发玩家会话时把当时的 `credentialVersion` 写进会话；
- 每次校验会话都比对该值与账号当前值，**不相等即视为失效**，无需逐个查找并删除会话记录；
- 改密（§3.4）、换邮（§3.5）、停用与软删除都必须递增它，从而一次性作废该账号的全部既有会话；
- 发起变更的当前设备在持久化成功后立即换发携带新版本的会话，因此不会被自己的操作踢出正在进行的对局。

### 唯一性与账号状态

唯一性约束有两个：`emailLookupHash`（登录标识）与 `nicknameNormalized`（展示名）。二者随账号状态变化的规则：

| 状态 | 邮箱占用 | 昵称占用 | 说明 |
| --- | --- | --- | --- |
| `active` | 占用 | 占用 | 正常账号 |
| `disabled` | **保留占用** | **保留占用** | 停用可恢复，其标识不能被他人顶替注册 |
| `deleted` | **释放** | **释放** | 软删除后可被重新注册 |

软删除必须清除昵称及其规范化索引、密码、邮箱密文与索引、头像等身份/凭证/资料字段。墓碑保留 `playerId`、`deletedAt`，以及 schema 校验和管理员生命周期列表所需的非敏感状态、版本与时间元数据；不得保留任何可用于登录、识别邮箱或恢复玩家资料的内容。同一邮箱重新注册会得到**全新的 `playerId`**，与墓碑记录之间没有任何关联，不继承其历史。

前向约束：ADR-0006 规划的 `playerId` 级 Agent 长期记忆一旦落地，软删除必须一并清理或转移该记忆，否则墓碑之外会留下按 `playerId` 关联的孤儿数据。当前 Agent 记忆按 attempt/levelRun/seat 归属、通关进度为全局共享，二者都不含 `playerId`，暂不受影响。

### 头像

`avatar` 保留（现有实现与 `Seat` 类型都在用，见 `server/src/auth/accountStore.ts` 与 `shared/src/state.ts`）：

- 玩家上传了头像时保存其标识，`avatar` 非空即使用它。
- 未上传时 `avatar` 为 `null`，由**内置的 2 张默认头像**兜底，按 `playerId` 派生索引选取：

  ```text
  defaultAvatarIndex = hash(playerId) % 2
  ```

- 采用派生而非注册时随机落库，是为了让结果确定、跨设备一致、重渲染不闪烁，同时不增加字段。
- **默认头像允许重复**：只有 2 张，4 人局出现两名玩家同图属预期行为，不做去重或抢占。座位区分依赖昵称与座位号，不依赖头像。

### 密码哈希

沿用现有 **scrypt** 实现（`server/src/auth/accountStore.ts` 的 `CURRENT_KDF`：N=16384, r=8, p=1, keylen=64），KDF 参数随记录版本化存储在 `kdf` 字段，将来加强成本参数时按字段兼容旧账号。

因此 schema 保留独立的 `passwordSalt`。不改用 Argon2id 的理由：Node 内置 `crypto.scrypt` 无需原生依赖，Railway 部署无额外构建风险，而现有实现已通过测试；本项目规模下 scrypt 的强度充分。若将来决定迁移 Argon2id，可借 `kdf.algo` 做双读平滑切换。

### 邮箱

邮箱规范化至少包含 `trim` 与域名小写；不要擅自删除 `+tag` 或点号。

唯一索引与密文使用**两个用途隔离的子密钥**，由单个主密钥 `ACCOUNT_EMAIL_KEY`（32 字节）经 HKDF 派生——同一段字节不应同时承担加密与 MAC 两种用途：

```text
indexKey  = HKDF(ACCOUNT_EMAIL_KEY, info="email-index")
cipherKey = HKDF(ACCOUNT_EMAIL_KEY, info="email-cipher")

emailLookupHash = HMAC-SHA-256(indexKey, normalizedEmail)
emailCiphertext = AES-256-GCM(cipherKey, iv, normalizedEmail)
```

用 keyed HMAC 而非裸 SHA-256 作索引，是因为邮箱空间可枚举——拿到账号文件的攻击者可以对候选邮箱字典逐个哈希比对，无密钥则构造不出这张对照表。

**`ACCOUNT_EMAIL_KEY` 丢失属不可恢复故障**：索引算不出、密文解不开，全部账号永久不可用，唯一出路是清库重注册。该密钥必须与账号库**分开**做同等级离线备份（同处泄露则加密失去意义）。`emailKeyVersion` 支持按版本双读轮换（旧密钥解密 → 新密钥重加密 → 重算索引），但前提是旧密钥仍可用，它是运维能力而非补救手段。

fail-closed 沿用现有语义：账号库或密钥异常时拒绝登录和注册，绝不写盘覆盖，也不退化为内存空库。

## 6. 服务端接口与事件

建议以现有 Socket 架构扩展：

- `account:register`：邮箱、密码、昵称、房间密码；成功返回会话；
- `account:login`：邮箱、密码、房间密码；
- `account:profile:update`：修改昵称，并可选替换自定义头像或以 `null` 恢复默认头像；
- `account:password:change`：当前密码 + 新密码；
- `account:email:change`：当前密码 + 新邮箱；
- `account:sessions:revokeOthers`；
- `admin:accounts:list`；
- `admin:accounts:forceLogout`；
- `admin:accounts:setStatus`；
- `admin:accounts:softDelete`。

管理员事件统一使用 `admin:accounts:*` 前缀，不混用单复数。

注册正常路径仍是“持久化账号后直接入座并返回会话”。若 scrypt/写盘期间房间被占满或已经开局，账号提交不得回滚；服务端必须私发账号资料与成功的 `register` 动作结果，并返回稳定错误码 `ACCOUNT_CREATED_ROOM_ENTRY_FAILED`，明确说明“账号已创建但未入房”，避免用户再次注册时才从“邮箱已注册”反推结果。

本期不得声明或暴露 verification、resend、recovery、reset 等“空实现”事件。

限流至少覆盖登录、注册、改密、换邮和管理员高风险操作；登录同时使用邮箱失败桶与连接地址总闸门，所有桶都必须过期清理并设置硬上限。所有管理员写操作记录操作者、目标 `playerId`、时间、原因与结果，不记录密码或完整邮箱。管理员写操作执行前先追加带 `auditId` 的 `pending` 记录，预写失败必须拒绝动作；动作完成后追加同 `auditId` 的最终结果，若最终追加失败，则以包含同一非敏感审计条目的结构化服务日志兜底，并把降级状态明确返回管理员。

## 7. 前端信息架构

```text
玩家
├─ /                         登录（邮箱 + 个人密码 + 房间密码）
├─ /account/register         注册并直接创建账号
└─ /account/security         头像、昵称、登录邮箱、个人密码、会话

管理员
└─ /admin
   ├─ /admin/accounts        账号维护
   └─ /admin/room            房间与座位维护
```

Prototype 使用 `/prototype/...` 对应路径。不存在 `/prototype/account/recover`。

登录和注册界面遵循“越简洁越好”：只有品牌、小型双 Tab、必要标题、字段、主按钮和一条限制提示；不放宣传标语、大幅时钟、身份模型解释或旧账号升级入口。

## 8. 开发阶段

### Phase 1：账号存储与显式注册（后端已完成）

- 建立 V2 repository、加密邮箱和密码哈希（沿用 scrypt，保留 `passwordSalt` 与 `kdf`）；
- `ACCOUNT_EMAIL_KEY` 主密钥与两个 HKDF 子密钥；
- 实现邮箱唯一登录与直接注册；
- 移除昵称隐式注册；
- 内置 2 张默认头像资源与 `hash(playerId) % 2` 的派生逻辑；
- 备份并重建开发期昵称账号，保留独立的全局通关进度。

### Phase 2：玩家自助维护（后端已完成）

- 上传、更换头像或恢复 `playerId` 派生的默认头像，并同步当前座位；
- 修改昵称；
- 当前密码修改密码；
- 当前密码修改登录邮箱；
- 会话撤销与安全限流。

### Phase 3：管理员账号维护（后端已完成）

- 账号列表、搜索、状态和脱敏邮箱；
- 强制登出、停用/恢复、软删除与审计；
- 保持房间管理与账号管理的动作边界。

### Future：域名与邮箱能力

只有满足以下条件后才重新立项：

1. 已购买并配置自有域名；
2. 邮件服务完成 DNS 验证并能向任意玩家邮箱稳定投递；
3. 注册验证、换邮验证和密码找回的安全流程与限流通过评审；
4. 对第一阶段未验证账号制定“重新验证或重注册”迁移方案。

未来功能不能把第一阶段账号自动视为邮箱已验证，也不能保留管理员重置密码作为旁路。

## 9. 验收标准

1. 首页默认是邮箱登录，认证卡片只有“登录 / 注册”两个 Tab。
2. 登录和注册都不出现邮箱验证码、发送邮件、找回密码或旧账号升级入口。
3. 注册完成后直接创建账号并进入大厅；邮箱仅检查格式与唯一性。
4. 页面清楚提示“邮箱不验证、密码无法找回”。
5. 昵称可在账号资料页修改，修改后仍使用邮箱登录。
6. 玩家只有在已登录且提供当前密码时，才能修改密码或登录邮箱。
7. 管理员看不到、不能代设或重置玩家密码，也没有任何发信操作。
8. 管理员请出玩家只释放座位；停用、删除账号必须在账号维护区执行。
9. 服务端不存在 verification、recovery、reset 或 Resend 相关的对外接口与必需环境变量。
10. 桌面端与移动端均可在无需横向滚动的情况下完成登录、注册和账号维护。
11. 房间密码错误时服务端不查询账号仓库、不执行任何密码哈希运算，且返回独立于账号错误的文案。
12. 昵称账号级唯一：注册或改名撞名被拒且只提示“该昵称不可用”；改名后 `playerId`、邮箱、进度、座位归属与会话均不变。
13. 改密或换邮成功后，该账号在其他设备上的会话立即失效，当前设备不掉线。
14. 停用后的账号其邮箱与昵称不能被他人注册；软删除后同一邮箱可重新注册，且获得新的 `playerId`。
15. 玩家可在账号资料页上传、更换或恢复默认头像；自定义头像跨重启保留，已入座时更新后立即反映到房间座位。
