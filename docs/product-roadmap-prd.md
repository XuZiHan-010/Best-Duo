# Take Time Web Prototype 产品 PRD 与路线图

> 本文是项目的产品总纲与版本路线图，负责回答“这个产品要做成什么、每个版本交付什么、怎样算完成”。具体规则以 [rules.md](../rules.md) 为权威来源；技术状态机、Socket 事件、数据模型与测试细节见 [plans/take-time-web-prototype.md](../plans/take-time-web-prototype.md)、[plans/backend-dev-plan.md](../plans/backend-dev-plan.md)、[plans/frontend-ui-plan.md](../plans/frontend-ui-plan.md) 与 [project_progress.md](../project_progress.md)。

## 1. 产品定位

Take Time Web Prototype 是一个私用的在线合作时钟谜题游戏原型，灵感来自 Libellud 合作桌游《Take Time》的核心体验：玩家先共同观察和讨论，随后进入禁止沟通的暗置阶段，只能通过有限的提示标记传递信息，最后揭示所有牌并检验 6 个时钟区段是否满足关卡条件。

产品目标不是复刻官方内容，而是验证这类“合作推理 + 禁沟通执行 + 结果复盘”的体验能否自然迁移到在线实时 Web 形态。公开部署或继续扩展时，必须避免使用未经授权的官方美术、官方完整规则文本或官方 40 关内容。

核心产品原则：

- 服务端是唯一权威状态来源，负责发牌、可见性遮蔽、行动校验、计时器、胜负判定和进度写盘。
- 前端只展示服务端状态并发送玩家意图，不自行判断胜负，也不自行推导隐藏牌值。
- 单局使用固定 24 张牌库：白色 1-12 与黑色 1-12，每局抽 12 张。
- 发牌前必须通过求解器校验可解性，确保玩家拿到的牌面至少存在一种通关方案。
- 已通关进度和设置需要持久化；进行中的对局可以保持在服务端内存中。
- 版本推进优先保持核心体验稳定，再扩展人数、agent 和托管能力。

## 2. 目标用户与使用场景

主要用户是小范围熟人玩家和开发/设计者自己。产品优先服务远程两人游玩、规则验证、关卡迭代和后续 AI agent 实验。

典型使用场景：

- 两名真人玩家远程进入同一房间，完成一局 2 人合作谜题。
- 房主选择已解锁或未通关关卡，带队按顺序推进。
- 玩家失败后查看揭示结果和条件校验，复盘策略并重试。
- 开发者新增关卡后，通过可解性校验和端到端流程确认关卡可玩。
- 未来 3/4 名真人玩家可以进入同一局，按人数自动适配发牌和回合。
- 未来真人玩家可以加入 AI agent 队友，或在离开时让 agent 接管座位。
- 未来全 agent 对局可以用于演示、回归、关卡压力验证和策略观察。

## 3. 当前架构与设计原则

当前技术栈：

- 前端：Vite + React + TypeScript。
- 后端：Express + Socket.IO。
- 共享层：`shared` 包维护前后端共用类型和事件定义。
- 运行时状态：服务端单进程内存对象维护唯一全局房间和进行中的对局。
- 进度持久化：Railway Volume 上的 JSON 文件保存已通关关卡与设置。
- 部署：Railway 单服务，构建前端静态资源后由 Express 托管，并通过 Socket.IO 做实时同步。

设计原则：

- 单房间优先：V1-V4 都以唯一全局房间为基础，不把多房间作为近期目标。
- 座位数组化：即使 V1 只开放 2 人，内部模型也应尽量向 N 个座位演进，减少 V2 重写成本。
- 行动者无关：真人 socket 事件和未来 agent 决策应进入同一动作层，由服务端统一校验。
- 可见性安全优先：隐藏手牌的数值/颜色、桌面暗牌的数值不能进入非授权客户端状态或 DOM；桌面暗牌颜色允许公开显示。
- 计时器权威：倒计时视觉可以在前端渲染，但超时判负和阶段推进必须由服务端决定。
- 可回归：每次扩展人数、agent 或托管能力，都要补齐服务端单测、Socket 流程测试和前端 E2E。

## 4. 核心游戏体验

V1-V4 的核心体验保持一致：

1. 玩家输入昵称进入唯一全局房间。
2. 玩家准备；第一个准备者成为房主。
3. 房主配置设置、进入选关并选择关卡。
4. 玩家共同观察时钟、关卡条件和规则说明，并在讨论阶段沟通策略。
5. 进入出牌阶段后禁止聊天，玩家按回合暗置手牌到 6 个区段。
6. 每次出牌后，出牌者可以消耗有限提示标记，将该牌永久翻开给全队看。
7. 12 张牌全部放完后自动揭示，服务端统计每段总和并校验关卡条件。
8. 成功则写入通关进度，并允许房主进入下一关；失败则允许重试或返回选关。

核心体验约束：

- 讨论阶段可以沟通；出牌阶段不能通过聊天沟通。
- 暗牌对所有玩家保持隐藏，只有提示标记翻开的牌和最终揭示阶段公开。
- 关卡条件、中心值、颜色规则和区段编号必须与 [rules.md](../rules.md) 和 [levels/README.md](../levels/README.md) 保持一致。
- 通关进度跨重启、重新登录保留。

## 5. V1：双人真人 MVP

### 目标

交付一个稳定可玩的 2 名真人玩家单房间 Web MVP，完整覆盖登录、准备、房主、选关、讨论、出牌、提示、揭示、结算、重试、下一关和进度持久化。

### 用户故事

1. 作为玩家，我想输入昵称加入房间，以便和另一名玩家快速开始游戏。
2. 作为房主，我想在两人准备后选择关卡，以便控制本局挑战。
3. 作为玩家，我想在讨论阶段查看关卡条件并聊天，以便共同制定策略。
4. 作为玩家，我想在出牌阶段看到自己的合法手牌可见性，以便按规则暗置手牌。
5. 作为玩家，我想在出牌后选择是否使用提示标记，以便用有限信息帮助队友。
6. 作为玩家，我想在揭示后看到每个区段总和和条件通过情况，以便复盘失败原因。
7. 作为房主，我想通关后进入下一关或失败后重试，以便连续游玩。
8. 作为回访玩家，我想重新登录后看到已通关关卡，以便从上次进度继续。

### 范围

- 单全局房间，最多 2 名真人玩家。
- 昵称登录，不做账号、密码、邮箱和第三方登录。
- 第一个准备者成为房主；房主负责设置、选关和推进。
- 2 人发牌规则：每人 6 张，中间 4 张初始对本人可见，两端 2 张对本人也隐藏；自己打满 2 张后翻开剩余盲牌给本人看。
- 固定 6 个区段，桌面暗置牌默认显示颜色、隐藏数值。
- 提示标记为全队共享额度。
- 前 4 关可玩，后续关卡按 `levels/` 继续补充。
- Railway 单服务部署和 Volume JSON 持久化。

### 非目标

- 不做 3/4 人开放。
- 不接入 AI agent。
- 不做中途 agent 接管。
- 不做多房间、观战、排行榜、账号体系和商业化。
- 不使用官方美术、官方完整规则文本或官方关卡全集。

### 主要能力

- 服务端维护权威状态机：`waiting -> levelSelect -> discussion -> placing -> reveal -> result`。
- Socket.IO 同步公共房间状态，并向每名玩家单独下发私有手牌视图。
- 运行时 payload 校验和服务端身份校验。
- 计时器幂等、断线/重连处理和房主转移口径。
- 条件引擎、关卡 loader、可解性求解器和通关进度写盘。
- 前端提供核心界面、响应式布局、键盘可达性和关键 E2E。

### 验收标准

- 两名玩家可以在本地双浏览器完成一局完整游戏。
- `npm run typecheck`、`npm test` 和前端 E2E 在目标环境通过。
- 隐藏牌值不会出现在非授权客户端状态或 DOM 中。
- 成功通关会持久化到 JSON，服务重启后仍能显示已通关。
- Railway 上页面加载、Socket 同步、Volume、重启恢复和 `SIGTERM` flush 行为通过验收。
- 当前优先级是完成 V1 M7 全量验收与回归，再进入 V2。

### 依赖与风险

- 真实 Railway Volume 和 WebSocket 行为仍需人工验收。
- 总关卡数 N 尚未确认，V1 只要求关卡体系可扩展和前 4 关可玩。
- 前端 review fixes 需要全量回归确认。

## 6. V2：3/4 人真人扩展

### 目标

在保持 V1 核心体验不变的前提下，开放 3 人和 4 人真人玩家同局游玩，让房主可以选择 `capacity`，并让发牌、回合、可见性、座位 UI 和测试全部按人数派生。

### 用户故事

1. 作为房主，我想选择 2/3/4 人容量，以便按当前人数开局。
2. 作为第 3 或第 4 名玩家，我想加入同一房间，以便参与多人合作谜题。
3. 作为玩家，我想看到所有座位、准备状态和当前回合，以便理解多人局进度。
4. 作为玩家，我想在 3/4 人局中拿到正确数量的手牌，以便按多人规则出牌。
5. 作为玩家，我想多人局仍然遵守隐藏桌面牌和提示标记规则，以便核心体验一致。

### 范围

- 开放 `capacity: 3` 和 `capacity: 4`。
- 3 人局每人 4 张，4 人局每人 3 张，牌库仍抽 12 张。
- 3/4 人手牌全部对本人可见，不使用 2 人局的端牌盲牌和打满 2 张翻牌机制。
- 第一手仍为抢先手，之后按座位顺序循环出牌。
- TopBar、Lobby、手牌区、回合提示、结算和 E2E 支持 N 个真人座位。

### 非目标

- 不引入 agent。
- 不做中途离开接管。
- 不做多房间匹配。
- 不改变关卡条件体系和 6 区段结构。

### 主要能力

- 后端解除 `capacity === 2` 锁定，补齐 schema、设置持久化和入座规则。
- 发牌、可见性和回合逻辑统一读取人数规则表。
- 前端座位和状态展示从固定 A/B 全面转为 `seats[]` 派生。
- 多人场景补齐服务端单测、Socket 流程测试和 Playwright E2E。

### 验收标准

- 2 人 V1 流程不回归。
- 3 人局可以完整完成讨论、12 张牌出牌、提示、揭示和结算。
- 4 人局可以完整完成讨论、12 张牌出牌、提示、揭示和结算。
- 3/4 人局中每名玩家只看到自己的手牌，不能看到其他玩家手牌。
- 3/4 人局不触发 2 人专属盲牌翻开规则。
- 多人移动端布局不遮挡核心操作。

### 依赖与风险

- V2 必须建立在 V1 M7 验收完成之后。
- 人数扩展会放大状态同步和 UI 布局复杂度，需要先以测试锁住 2 人回归。
- 多人局的等待、离开和房主转移口径需要与 V1 断线规则兼容。

## 7. V3：AI Agent 玩家

### 目标

引入 AI agent 作为可加入房间的玩家，让真人玩家可以在人数不足时补足队友，并验证 agent 在讨论、出牌和提示决策中的可玩性。

### 用户故事

1. 作为房主，我想给空座加入 AI agent，以便在真人不足时开始游戏。
2. 作为 2 人玩家队伍，我们想加入 1 或 2 个 agent，以便体验 3/4 人合作局。
3. 作为 3 人真人队伍，我们想加入 1 个 agent，以便补足 4 人局。
4. 作为玩家，我想在讨论阶段看到 agent 的发言，以便把它当作队友协作。
5. 作为玩家，我想看到 agent 的思考中状态，以便理解当前等待原因。
6. 作为开发者，我想 agent 通过同一动作层出牌和做提示决策，以便服务端规则不分真人和机器。

### 范围

- 房主可以在开局前向空座添加或移除 agent。
- agent 座位与真人座位共享 `Seat` 模型，以 `kind: 'agent'` 区分。
- agent 能在讨论阶段读取允许的信息并发言。
- agent 能在轮到自己时选择手牌和区段。
- agent 能在出牌后决定是否使用提示标记。
- agent 决策必须经过服务端动作层和相同校验。
- agent 超时或异常时有服务端兜底策略，不能卡死房间。

### 非目标

- 不要求 agent 接管中途离开的真人座位。
- 不要求全 agent 对局。
- 不要求 agent 具备长期个人账号记忆。
- 不让前端直接调用 LLM API。
- 不把 agent 作为规则裁判；胜负仍由服务端条件引擎判定。

### 主要能力

- 后端实现 `PlayerAgent` 和 `agentDriver`，把 agent 的讨论、出牌和提示决策接入现有动作层。
- 为 agent 构造经过遮蔽的 `AgentRoomView`，只能包含该座位按规则可见的信息。
- 前端展示 agent 座位、agent 消息样式、房主加/撤 agent 入口和 agent 思考状态。
- 配置 LLM provider、模型、超时、重试和降级策略，敏感密钥只放服务端环境变量。

### 验收标准

- 2 真人 + 1 agent 可以完成 3 人局。
- 2 真人 + 2 agent 可以完成 4 人局。
- 3 真人 + 1 agent 可以完成 4 人局。
- agent 不能看到超出座位权限的隐藏牌值。
- agent 决策异常不会导致房间永久卡住。
- 真人玩家仍可区分哪些座位和消息来自 agent。
- V1/V2 真人-only 流程不回归。

### 依赖与风险

- V3 依赖 V2 的 N 座位、N 人回合和多人 UI 稳定。
- LLM 输出不稳定，必须用结构化解析、重试和兜底策略控制风险。
- agent 可能破坏游戏乐趣，需要后续调参和提示词迭代。

## 8. V4：AI 接管与全 Agent 对局

### 目标

让 AI agent 不只是开局前补位，也能在玩家中途离开或主动选择托管时接管座位；同时支持 4 个 agent 自行完成对局，用于演示、回归、关卡验证和策略观察。

### 用户故事

1. 作为玩家，我想在临时离开时选择 AI 托管，以便不中断队友游戏。
2. 作为房主，我想在玩家掉线超过阈值后让 agent 接管，以便避免房间卡死。
3. 作为离开的玩家，我想回来后重新接回自己的座位，以便继续参与游戏。
4. 作为开发者，我想启动全 agent 对局，以便快速跑通关卡和回归流程。
5. 作为观察者，我想查看 agent 对局过程和结果，以便评估关卡设计与 agent 策略。

### 范围

- 真人座位支持主动切换为 agent 托管。
- 玩家断线或离开达到规则阈值后，可由房主或系统策略触发 agent 接管。
- 原玩家重连后可以按规则取回座位。
- 接管前后的座位归属、昵称、消息和行动记录清晰可追溯。
- 支持 4 个 agent 组成完整对局。
- 全 agent 对局可用于开发、演示和测试，不要求成为面向普通玩家的主入口。

### 非目标

- 不做跨设备长期账号托管。
- 不做复杂权限系统。
- 不保证 agent 达到人类高手水平。
- 不把全 agent 对局作为 V3 的验收要求。

### 主要能力

- 座位需要区分原真人归属、当前控制者和连接状态。
- 服务端支持控制权交接：human -> agent、agent -> human。
- 计时器和回合逻辑在接管发生时保持幂等，不误判超时。
- 前端明确展示托管、离线、agent 控制和可取回状态。
- 全 agent runner 可以驱动一局从讨论到结算的完整流程。

### 验收标准

- 真人主动托管后，agent 能接替其后续讨论、出牌和提示决策。
- 真人断线后，房间可以按规则进入 agent 接管，不永久停在等待状态。
- 真人重连后，可以安全取回座位，且不会看到不该看的历史隐藏信息。
- 4 agent 对局可以自动完成一局并输出结果。
- 接管过程不会破坏进度持久化、胜负判定或可见性遮蔽。
- V1-V3 的正常真人/agent 混合开局流程不回归。

### 依赖与风险

- V4 依赖 V3 的 agent 决策能力稳定。
- 控制权交接会显著增加状态复杂度，需要更强的端到端测试。
- 玩家回来后的信息边界尤其敏感，必须防止通过接管历史泄漏隐藏牌值。

## 9. 跨版本验收标准

每个版本都必须满足以下横向标准：

- 服务端权威：所有关键校验、胜负判定、计时器结果和进度写盘都在服务端。
- 可见性安全：隐藏手牌的数值/颜色、桌面暗牌的数值只下发给有权限的接收者；桌面暗牌颜色可公开。
- 可解性保障：每局抽牌后先用求解器确认至少存在一种解。
- 回归稳定：新版本能力不能破坏低版本核心流程。
- 可访问性：核心操作键盘可达，焦点管理、弹窗、倒计时和移动端布局可人工验收。
- 部署可用：Railway 单服务构建、启动、健康检查、Socket 同步和 Volume 持久化可验证。
- 文档同步：规则改动同步 `rules.md`，关卡新增同步 `levels/README.md`，技术计划改动同步 `plans/`。

建议测试层级：

- 条件引擎、发牌规则、可见性、计时器和动作层使用服务端单测覆盖。
- 入座、准备、选关、出牌、提示、揭示和结算使用 Socket 流程测试覆盖。
- 关键 UI、移动端布局、焦点管理、断线禁操作和隐藏牌防泄漏使用 Playwright E2E 覆盖。
- Railway 行为使用人工验收清单覆盖。

## 10. 非目标与版权边界

长期非目标，除非后续单独立项：

- 多房间大厅、匹配系统和公开玩家社区。
- 正式账号体系、好友系统、排行榜和成就系统。
- 商业化、付费关卡或公开大规模运营。
