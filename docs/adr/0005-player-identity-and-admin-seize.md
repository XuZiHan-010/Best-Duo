# ADR-0005：玩家会话凭证与管理员强制接管

- 状态：Accepted
- 日期：2026-07-16
- 实施计划：[玩家身份安全与管理员强制接管](../../plans/2026-07-15-player-identity-and-admin-control-plan.md)

## 背景

旧实现把"正确房间密码 + 相同昵称"视为原玩家重连：服务端发现在线同昵称后先断开旧 socket，再把新 socket 附着到原座位。任何知道共享房间密码和昵称的人都能接管座位、房主身份、私有手牌与出牌权限。同时产品缺少一个能在满房或对局卡死时收回房间的管理员入口；现有 `room:reset` 仅限非生产环境。

## 决策一：昵称不作为身份凭证，座位所有权由服务端签发的会话凭证证明

- 首次成功入座时服务端签发 `playerId` + 高熵 `reconnectToken`，只经私发事件 `player:session` 返回；服务端仅保存 SHA-256 摘要（`server/src/auth/playerSessions.ts`）。
- 重连/接管唯一凭据是会话凭证：Socket.IO handshake `auth` 自动重连，或 `player:join.session` 显式接管；每次成功附着都轮换令牌，旧令牌保留 30 秒宽限期，防止"服务端已轮换、客户端落盘前断网"把合法玩家锁死。
- 无有效会话的同昵称加入一律 `NICK_IN_USE`，原座位与旧连接零影响；顺序固定为"先验证、附着并轮换成功，最后断开旧 socket"，防止新连接先踢旧连接的拒绝服务。
- 玩家离开、被请出、座位超时释放、房间软重置时撤销会话；仓库为纯内存、一房一仓库（`WeakMap<GameRoom, PlayerSessionStore>`），房间换代后旧令牌自然作废。
- 公共座位改为显式 `PublicSeat` 白名单，替代 `Omit<Seat, "socketId">`，杜绝未来新增内部字段被意外广播。

## 决策二：管理员不设旁观角色，进入房间即确认制强制接管并入座为房主

- 管理员登录成功后：若其玩家会话仍在座则直接恢复；若房间有真人则必须先经客户端弹窗确认（"当前房间有玩家正在游戏，是否要强制进入房间并终止当前游戏？"），选"否"零副作用；确认后原子执行——终止游戏、全员收到"管理员已强制结束当前游戏，您已被请出房间"并被请出、撤销全部会话、管理员入 A 座成为房主。
- 接管后管理员占用真实 `Seat`（`kind='human'`）并持有普通玩家会话（内部 `isAdmin` 标记），刷新/断线走玩家路径恢复，不会二次清场；`SeatKind`、`host: SeatId`、`capacity` 语义均无需改动。
- `admin:seizeRoom` 与 `admin:kickPlayer` 必须携带确认时的 `stateVersion`，服务端拒绝陈旧操作，防止基于过期弹窗清掉一局刚开始的游戏。
- 凭证为独立环境变量 `ADMIN_USERNAME`/`ADMIN_PASSWORD`（不得等于 `ROOM_PASSWORD`），恒定时间比较 + 失败限流 + 统一错误文案；入座昵称单独填写，账号名永不进入公共状态。
- 接管与对局中请出不写通关进度、不记 `rule-unmet`/`timeout`/`player-left` 失败。

### 被否决的替代方案：只读管理面板 + 非座位管理员角色

- 与"管理员可加入座位、进行游戏"的产品诉求正面冲突，权限矩阵自相矛盾。
- `host: SeatId` 意味着房主必须是座位；非座位房主需要全局改造 `host` 类型与所有前端判断。
- 实际需求（收回自己的私用房间）不存在"只看不动"的场景，面板是无收益的复杂度。

## 后果

- 客户端会话存 `sessionStorage`（同标签页），跨标签恢复留待评估 HttpOnly Cookie；令牌不进 URL/DOM/日志。
- 被请出者在共享密码模式下可换新昵称重新加入——这是"请出"而非封禁；可靠封禁需另行引入可撤销账号或邀请名单。
- 管理员登录入口为独立 `/admin` 页面，玩家登录页不展示任何管理员痕迹（避免玩家好奇尝试触发全局限流、锁住真正的管理员）。
- E2E 全量覆盖：同昵称抢座被拒、会话刷新恢复、接管否/是两路径、刷新不二次清场、单点请出与重新加入。
