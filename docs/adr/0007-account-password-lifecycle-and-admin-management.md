# ADR-0007：第一阶段采用未验证邮箱登录，延期密码找回

> 状态：已接受（2026-07-20）  
> 关联：[ADR-0005](0005-player-identity-and-admin-seize.md) · [ADR-0006](0006-player-accounts-and-deferred-agent-memory.md) · [详细设计](../../plans/2026-07-20-email-identity-recovery-and-admin-management-design.md)

## 背景

产品希望从“昵称 + 个人密码的隐式注册”切换到玩家熟悉的邮箱账号。但邮件验证和密码找回不仅需要 Resend 等发送 API，还需要可验证的自有发信域名。项目现阶段不准备承担域名与邮件投递成本，因此不能把尚不可用的邮件能力放进产品流程。

同时，昵称和房间密码都不是个人秘密，管理员的线下判断也不能证明申请者是原账号本人。没有可靠的身份验证渠道时，提供管理员重置或恢复密钥流程会形成账号接管风险。

## 决策一：邮箱暂时只作为未验证的唯一登录标识

- 新用户显式填写邮箱、个人密码、昵称和房间密码注册。
- 服务端只校验邮箱基础格式与唯一性，注册成功后立即创建账号。
- 日常登录使用“邮箱 + 个人密码”，进入房间时另行校验房间密码。
- 内部身份始终使用稳定 `playerId`；昵称可修改，只用于展示。
- 产品不得称邮箱“已验证”或暗示它能证明账号所有权。

## 决策二：第一阶段不提供密码找回

- 不实现 `/account/recover` 与登录页找回入口。生产代码中这两者从未存在，需要移除的只有原型里的对应页面与 Tab。
- 不实现邮件验证码、重置链接、恢复密钥或管理员签发凭证。
- 忘记密码时无法恢复原账号；登录和注册页必须明确提示用户妥善保管密码。
- 房间密码不能用于找回，因为它是多人共享的准入口令。

## 决策三：管理员不是密码托管人

- 管理员不能查看、导出、代设或重置玩家密码。
- 管理员不能替玩家更换邮箱，也不能把邮箱标记为已验证。
- 管理员可以强制登出、停用/恢复、软删除账号，以及在独立房间页请出玩家。
- “请出房间”只释放座位，不改变注册账号状态。

## 决策四：玩家可在当前密码保护下修改账号资料

- 昵称由有效会话直接修改。
- 个人密码由“有效会话 + 当前密码”修改，成功后撤销其他会话。
- 登录邮箱由“有效会话 + 当前密码”修改，并立即成为新的未验证登录标识；只校验格式和唯一性。
- 未来启用邮件能力时，换邮必须升级为验证新邮箱并通知旧邮箱，不能沿用当前简化流程。

## 决策五：邮件基础设施整体延期

第一阶段不引入 Resend、SMTP、`TransactionalEmailProvider`、发信域名或相关环境变量，也不暴露 verification、resend、recovery、reset 空接口。

只有购买并验证自有域名、确认邮件投递能力并完成安全评审后，才另行实施邮箱验证和密码找回。届时第一阶段账号必须重新验证或重注册，不能被自动标记为已验证。

## 结果

### 正面

- 注册路径短，现阶段不依赖外部邮件服务和域名。
- 登录标识与可修改昵称分离，内部身份稳定。
- 不用虚假的“找回”功能制造账号接管后门。
- 前端认证入口收敛为简洁的“登录 / 注册”双 Tab。

### 代价与风险

- 邮箱填错或被冒填时系统无法识别。
- 用户忘记密码会永久失去该账号。
- 管理员无法帮助真正的账号所有者找回账号。
- 正式开放邮件验证前，开发期账号需要专门迁移或重建。

这些限制必须在 UI 中明确说明，并依靠私用房间密码、注册限流和小范围部署降低第一阶段风险，但这些措施不构成邮箱所有权证明。

## 被否决的替代方案

- **继续使用昵称登录**：昵称公开且可修改，不适合作为稳定登录键。
- **用昵称 + 房间密码找回**：两者均非个人秘密，任何知情房间成员都可能接管账号。
- **管理员人工重置密码**：系统无法验证申请人身份，会让管理员成为账号接管入口。
- **恢复密钥作为临时方案**：普通玩家很难长期保存；丢失后仍无法恢复，并增加产品和运维复杂度。
- **只接 Resend 不买域名**：共享测试域名不能满足真实多玩家投递，无法形成可用产品能力。
- **保留灰色的找回入口等待以后启用**：会让用户误以为账号可恢复；本期完全不展示。
